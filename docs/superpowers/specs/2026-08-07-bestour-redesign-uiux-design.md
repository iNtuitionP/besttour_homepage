## 1. 목표

노후화된 베스트투어 홈페이지를 현대적으로 리디자인한다. 이번 단계의 산출물은 **구현이 아니라 클라이언트(사장님) 컨펌용 UIUX 시안**이다.

핵심 원칙:
- **견적이 최우선.** 방문자가 버스 대절 사이트에 오는 이유는 견적이다. 견적 기능을 홈 전면(히어로)에 배치한다. 연혁·인사말류는 전면에서 제외하되 삭제하지 않는다.
- **기존 기능/메뉴 100% 보존.** 삭제 없이 재배치만 한다.
- **보라색 아이덴티티 유지 + 모던화.** 실제 버스가 보라색("보라색버스"가 브랜드 자산). 촌스러운 보라 원색을 세련된 톤(딥퍼플/바이올렛 + 뉴트럴)으로 재해석한다.

## 2. 이번 단계 산출물

- 클릭 가능한 **고충실도 정적 HTML 시안** — 백엔드 없음, 브라우저에서 바로 열람
- 견적 위저드는 **더미 요금표로 실시간 가격 계산이 실제 동작**하는 프로토타입 (실제 요금표는 추후 사장님에게 받아 교체)
- 저장 위치: 저장소 `mockups/` 폴더
- 홈 화면 시안 6개 + 핀 기능 있는 비교 갤러리 페이지
- 선택안 확정 후: 견적 위저드 상세 + 서브페이지 확장

구현(그누보드 대체, 백엔드, 배포)은 시안 컨펌 후 별도 단계.

## 3. 견적 기능 정책 (사용자 확정)

- 위저드에서 **예상 가격을 실시간으로 표시**한다 (더미 요금표 기반).
- 사용자는 **예약을 걸 수 있다**. 온라인 결제는 하지 않는다.
- **예약 확정은 사장님이** 한다. 확정된 예약에 대해서만 결제가 진행된다 (오프라인/추후).
- 완료 화면 문구: "사장님 확정 후 연락드리며, 확정된 예약만 결제 진행됩니다."

### 13.9 사진 용량 정책 — "사진 많이 올리고 싶다"에 대한 답 (2026-09-06 확정)

**원칙: 사진 바이너리는 Postgres에 넣지 않는다.** Supabase Storage 버킷에 저장하고 DB(`gallery`)에는 경로만 기록한다 — `0001_init.sql` 설계 그대로. 따라서 "DB를 얼마나 키워야 하나"는 사실상 논점이 아니고, 실제로 봐야 할 축은 **Storage 용량**과 **전송량(egress)** 두 가지다.

**(1) Postgres — 10년 누적 추정**

| 테이블 | 행당 | 10년 가정 | 용량 |
|---|---|---|---|
| gallery | ~250B | 10,000장 | 2.5MB |
| reservations | ~1.2KB | 연 2,000건 × 10년 | 24MB |
| notifications_log | ~400B | 예약당 4건 | 32MB |
| notices·popups·vehicles·showcase_routes | — | 수백 행 | <1MB |
| 인덱스·오버헤드(+40%) | | | ~24MB |
| **합계** | | | **≈ 85MB** |

Pro 포함량 8GB의 **1%**. DB 용량은 고려 대상이 아니다.

**(2) Storage — 사진**

폰 원본 4000×3000 ≈ 3~5MB. 업로드 시 자동 변환: 1600px WebP ≈ 250KB(본문) / 800px ≈ 90KB(카드) / 400px ≈ 30KB(썸네일) = 장당 변환본 ≈ 370KB.

| 사진 수 | 변환본만 | 원본까지 보관 |
|---|---|---|
| 500장 | 0.2GB | 2.2GB |
| 2,000장 | 0.7GB | 8.8GB |
| 10,000장 | 3.7GB | 44GB |

Pro 포함 100GB. **1만 장을 원본까지 전부 보관해도 포함 범위 안**이며 추가 비용 0.

**(3) Egress — 실제 비용을 결정하는 축**

Pro는 월 250GB 포함, 초과 $0.09/GB. 갤러리 1회 조회 ≈ 썸네일 24장(0.7MB) + 상세 몇 장. 세션당 평균 2.5MB로 잡으면 월 10,000세션 = 25GB(포함량의 10%), 월 100,000세션 = 250GB로 경계선. 그 전에 CDN 캐시가 대부분 흡수한다. 즉 **전세버스 홈페이지 트래픽 규모에서는 상한에 닿지 않는다.**

**(4) 확정 정책**

| 항목 | 값 |
|---|---|
| 장당 업로드 상한 | 20MB (폰 원본 그대로 허용) |
| 허용 형식 | jpg / jpeg / png / heic / webp |

**(5) 이 정책이 요구하는 스키마·화면 변경 (미구현 — 다음 태스크)**

- `gallery`에 `width`, `height`, `bytes`, `original_path`, `album_id`, `created_at` 추가. width/height는 레이아웃 시프트(CLS) 방지에 필요하고 bytes는 사용량 모니터링에 쓴다.
- **앨범/카테고리 도입 필수** — 현재 `gallery`는 `sort int` 하나로 정렬하는 평면 목록이다. 사진이 수백 장만 넘어도 사장님이 관리할 수 없고 방문자도 못 본다. `gallery_albums`(차량별·행사별) + 페이지네이션/무한스크롤이 있어야 "많이 올리고 싶다"가 실제로 성립한다.
- admin 갤러리 탭: 다중 업로드, 드래그 정렬, 앨범 이동, 현재 사용량(장수·GB) 표시.

**여기서 확정되는 설계 변경 1건**

전자상거래법 §13②3호 때문에 무가격 화면이라도 **"견적이 무엇을 보고 정해지는지"를 화면에 표시**해야 한다.
