"고치지 않기로 했다"도 결정이다 — 근거 없이 잊히는 것만 막는다.

## D1. 매칭된 라우트가 `notFound()` 를 부르면 404 문서가 깨진다

**발견**: 2026-09-13, P6-3 독립 리뷰 F1(`P6-3-review.md`). 컨트롤러가 프로덕션 빌드로 재현·원인 규명.

### 실측 (`npm run build` → `next start`, 2026-09-13)

| URL | 상태 | `<html>` | 스크립트 제외 body |
|---|---|---|---|
| `/no-such-page` (매칭 없음) | 404 | `<html lang="ko">` | 567자 (정상) |
| `/fr`, `/ko-KR/x` (매칭 없음) | 404 | `<html lang="ko">` | 정상 |
| `/notices/999999` (매칭 후 `notFound()`) | 404 | `<html id="__next_error__">` | **266자 — 사실상 빈 화면** |
| `/notices/does-not-exist` (매칭 후 `notFound()`) | 404 | `<html id="__next_error__">` | **266자** |

내용이 사라진 것은 아니다. 404 문구·전화번호는 RSC 스트림 payload 안에 있고 `<div hidden><template id="B:0">` 슬롯에 대기한다 —
**JS 가 켜져 있으면 클라이언트가 채워 넣어 정상으로 보인다.** JS 가 없으면 빈 화면이고, `lang` 속성이 없어 스크린리더·검색엔진이 언어를 모른다.

### 원인 (실험 3회로 좁힘)

Next 15 는 **root layout 이 `<html>`/`<body>` 를 만든다**고 가정한다. 이 저장소는 ADR-1(P0-0)에 따라 `app/layout.tsx` 를
통과용으로 두고 `app/[locale]/layout.tsx` 가 껍데기를 만든다. 그래서:

- **매칭 없는 URL** → `app/not-found.tsx` 가 **스스로 `<html>` 을 렌더**하므로 정상(REVIEW-FIX M1 때 그렇게 고쳤다).
- **매칭된 라우트의 `notFound()`** → Next 가 껍데기를 만들 층을 찾지 못해 내장 `__next_error__` 셸을 쓰고, 그 안에 우리 `<html>` 이
  중첩돼 브라우저가 버린다.

반증한 가설(전부 재현 실패 → 원인 아님):
1. `app/[locale]/(site)/not-found.tsx` 가 원인 → **파일을 치우고 빌드해도 동일**(root 로 폴백해도 `__next_error__`).
2. ISR(`revalidate = 600`) 이 원인 → **`force-dynamic` 으로 바꿔도 동일**(`ƒ` 확인).
3. 경로 형식 검증 실패만의 문제 → **형식이 맞는 없는 id(`/notices/999999`)도 동일**.

### 지금 영향을 받는 경로

~~`notFound()` 를 부르는 라우트는 `/notices/[id]` 하나다.~~ → **2026-09-15 갱신: 둘이 됐다.**

| 경로 | 언제 | 비고 |
|---|---|---|
| `/notices/[id]` | 없는·미공개 공지 | 2026-09-13 확인 |
| `/gallery/[album]` | 없는·비활성·형식 위반 앨범 slug | **P6-3b 가 추가**(2026-09-15) |

옛 사이트 URL 은 전부 매칭 없는 URL 이라 여전히 정상 경로를 탄다.
P6-3 이 만든 결함이 아니다 — `/dev/krmap` 삭제 이후 이 경로를 아무도 실행하지 않아 드러나지 않았을 뿐이다.

**P6-3b 실측(2026-09-15)**: `/gallery/does-not-exist` 의 404 문서는 `/notices/does-not-exist` 와 **스크립트 제외 본문이 sha256 까지 동일**(`463c4788…`, 266자, `<html id="__next_error__">`, `lang` 없음)이다.
**새 변종이 아니라 같은 하나의 결함**이다. 한 가지 확인된 완화: 부재 분기의 `robots: noindex` 는 **JS 없이도 껍데기에 실려 나간다** — 검색엔진이 빈 문서를 색인하지는 않는다.

### 선택지

| # | 방법 | 비용 | 위험 |
|---|---|---|---|
| A | `app/layout.tsx` 가 `<html lang>`·`<body>` 를 만들고 `[locale]/layout.tsx`·`app/not-found.tsx` 는 껍데기를 뺀다 | 구조 변경(ADR-1 개정) · 레이아웃/에러/404 테스트 다수 | root 는 로케일을 모른다 → `lang` 을 기본값 고정하거나 `headers()` 를 읽어야 하고, 후자는 **홈의 정적 프리렌더(ISR)를 깬다** |
| B | 없는 공지 id → `/notices` 로 리다이렉트(soft-404) | 작다 | 없는 리소스에 404 를 주지 않는다(SEO soft-404). 공지 id 는 옛 사이트에 공개된 적이 없어 실피해는 작다 |
| C | 그대로 두고 문서화 | 0 | JS 없는 방문자에게 빈 404, `lang` 누락 |

### 현재 결정 (컨트롤러, 2026-09-13)

**C — 그대로 두고 기록한다. 단 CI 는 이 경로에서 상태코드 404 만 단언하고 문서 껍데기는 단언하지 않는다**(거짓 green 방지).
근거: (a) 영향 경로가 하나이고 옛 URL 전부는 정상 경로를 탄다, (b) A 는 홈 ISR 을 깨뜨릴 위험이 있어 별도 태스크와 독립 리뷰가 필요하다,
(c) B 는 404 의미를 바꾸는 제품 결정이라 사장님 확인 없이 하지 않는다.

### 결정 재확인 (컨트롤러, 2026-09-15) — **C 유지, 근거 (a) 는 폐기**

`/gallery/[album]` 이 생기면서 **근거 (a) "영향 경로가 하나" 는 더 이상 사실이 아니다.** 그대로 두면 낡은 근거로 결정을 떠받치는 셈이라 여기서 명시적으로 버린다.
그럼에도 **C 를 유지**하는 이유는 다음 셋이고, (a) 와 달리 이것들은 실측에 근거한다:

1. **한 결함이지 두 결함이 아니다.** 두 경로의 404 문서가 sha256 까지 같다 — 고치면 한 번에 둘 다 고쳐진다. 경로가 늘어도 **작업량은 늘지 않는다.**
2. **색인 피해가 없다.** `robots: noindex` 가 JS 없이도 껍데기에 실린다(P6-3b 실측). soft-404 로 바꿔 얻을 SEO 이득이 크지 않다.
3. **(b)·(c) 는 그대로 유효하다.** A 는 홈 ISR 을 깨뜨릴 위험이 있어 독립 리뷰가 필요하고, B 는 여전히 사장님 확인이 필요한 제품 결정이다.

**P6-3b 가 `/gallery/does-not-exist` → 404 단언을 CI 에 추가**했다(상태코드만 — 결정대로 문서 껍데기는 단언하지 않는다). 이제 두 경로가 매 푸시 검사된다.

**오픈 전 재검토 필수** — 플랜 §8 오픈 게이트에 항목으로 등록돼 있다. A 를 고르면 태스크 하나(레이아웃 구조 + 404 **3경로** 재실측 + 홈 ISR 유지 확인)로 처리한다.
경로가 셋째로 늘어나면 **그때는 C 를 재검토하라** — 반복해서 늘어난다는 것은 구조가 그 모양을 계속 만든다는 뜻이다.

## D2. Supabase 호스팅 프로젝트 인증 설정 — 조치 1건 + 전환 전 필수 2건

**발견**: 2026-09-13, P5-1/P5-2 독립 리뷰 A4. 리뷰어가 `supabase/config.toml`(로컬)에서 공개 가입 허용을 발견 → 컨트롤러가 **호스팅 프로젝트 실설정**을 Management API 로 조회해 확인.

### 조치 완료 — 공개 회원가입 차단 (2026-09-13)
조회 결과 `disable_signup: false` 였다. anon 키는 브라우저 번들에 실리는 공개 값이므로, 누구나 `POST /auth/v1/signup` 으로 `authenticated` 계정을 만들 수 있는 상태였다.
0009 가 `authenticated` 역할에 여섯 개 콘텐츠 표의 insert/update/delete 권한을 주므로, **RLS(`is_admin()`)가 유일한 방어선**이었다(리뷰어 손 추적: 노출은 0행이지만 방어선이 하나뿐).
→ Management API 로 `disable_signup: true` 적용. 재조회 확인. 사용자 수 적용 전후 **0 → 0**.
관리자 로그인에는 영향이 없다: 기존 사용자의 OTP 로그인은 가입이 아니고, 첫 관리자는 admin API 로 만든다(가입 플래그를 우회한다).
되돌리려면 같은 API 로 `false`. **다시 켜지 말 것** — 이 사이트에 공개 회원가입은 존재하지 않는다.

### 전환(P7) 전에 반드시 — 아직 미조치
| 항목 | 현재 값 | 왜 문제인가 |
|---|---|---|
| `smtp_host` | `null` (Supabase 기본 메일) | 기본 메일은 **시간당 2통**(`rate_limit_email_sent: 2`)이고 운영용이 아니다. 사장님이 로그인 링크를 두 번 받으면 그 시간엔 더 못 받는다. 그리고 `actions/admin/auth.ts` 는 발송 실패를 "보냈습니다"로 삼킨다 → **사장님이 영문도 모르고 못 들어온다.** 커스텀 SMTP(네이버웍스·Resend)를 붙이거나, 최소한 이 한도를 사장님께 알려야 한다 |
| `site_url` | `http://localhost:3000` | 매직링크가 localhost 로 간다. 운영 도메인으로 바꾸지 않으면 사장님 링크가 죽는다 |
| `uri_allow_list` | 빈 값 | 콜백 URL 허용 목록. 운영·프리뷰 콜백 주소를 넣어야 한다 |

세 항목 모두 플랜 §8 오픈 게이트에 등록한다.

## D3. 아웃박스 claim 이 채널을 가리지 않아 **사장님 알림만 조용히 죽는다**

**발견**: 2026-09-15, 컨트롤러가 P4-5 브리프를 쓰며 claim 함수와 문자 어댑터의 계약을 대조하다 발견. 코드 실측.

### 무슨 일이 벌어지나
사장님 번호(`OWNER_PHONE`)가 없으면 `planNotifications`(`lib/notify/outbox.ts:99-108`)가 사장님 행을 `channel='email'` 로 만든다 — 설계상 옳은 폴백이다.
그런데 `claim_pending_notifications(p_limit)`(`supabase/migrations/0005_outbox.sql:98-112`)의 where 절에는 **`channel` 조건이 없다.** 발송기는 문자 어댑터 하나만 들고 그 메일 행까지 집는다.
문자 어댑터는 `lib/notify/solapi.ts:288-290` 에서 `unsupported_channel` 을 **`retryable:false`** 로 돌려준다.

> **정정 (2026-09-16, P4-5 실측).** 처음에 여기 "한 번에 영구 `failed`" 라고 적었는데 **틀렸다.**
> `retryable` 은 **기록용 로그 필드일 뿐**이고(`sender.ts:34`), give_up 판정은 오직 `attempts`(`outbox.ts:129` `attempts >= MAX_ATTEMPTS`)가 한다.
> 실제 거동은 **크론이 돌 때마다 매번 집혀 `attempts` 가 1→5 로 오른 뒤 `failed` 로 종착**한다(실측: `attempts 추이 [1,2,3,4,5]`).
> 결과는 같다 — 사장님 알림은 죽는다. 다만 **한 번이 아니라 다섯 번에 걸쳐** 죽고, 그 사이 `last_error` 에 `unsupported_channel:email` 이 남는다.
> 같은 오해가 P4-2b 브리프에도 있었고 독립 리뷰가 잡았다. `retryable:false` 를 "즉시 포기" 로 읽지 마라.

**결과**: 솔라피 키를 넣는 순간 **고객 문자는 정상적으로 나가고 사장님 알림만 실패로 죽는다.** 예약이 들어온 것을 사장님은 관리자 화면에 직접 들어가야만 안다.
사장님 질문 **A-13** 이 말한 상태가 이것이고, 지금까지는 "메일 발송이 미구현"으로만 적혀 있었다. 실제로는 **미구현보다 나쁘다** — 행이 조용히 소멸한다.

### 왜 기계 게이트가 못 잡았나
`worker.ts` 헤더의 대원칙 — "sender 가 미구성이면 claim 자체를 하지 않는다"(attempts 는 되돌릴 수 없다) — 은 **sender 전체**에만 적용되고 **채널 단위로는 적용되지 않는다.**
테스트는 문자 경로만 실증했고, 메일 행이 있는 상태에서 문자 sender 만 구성된 조합을 아무도 만들어 보지 않았다. 조합이 비어 있으면 green 이다 — 2026-09-11 법정 문안 사고(빈 값 숨김)와 같은 모양이다.

### 조치
**P4-5 에서 고친다.** 세 가지를 함께 한다:
1. `0014_claim_by_channel.sql` — claim 에 채널 화이트리스트(`p_channels`)를 넣는다. 보낼 수 없는 채널의 행은 **집지 않는다**(attempts 가 보존된다).
2. `NotificationSender.channels` — sender 가 자기가 보낼 수 있는 채널을 선언하고 워커가 그것을 claim 에 넘긴다.
3. `lib/notify/mail.ts`(Resend) + `lib/notify/router.ts` — 메일을 실제로 보낼 수단과, 채널별로 나누는 라우터.

**오픈 전 필수.** 1·2 만 해도 "조용히 죽는" 것은 멈추지만(행이 pending 으로 남아 키가 온 뒤 나간다), 사장님이 알림을 **받으려면** 3 또는 `OWNER_PHONE` 이 필요하다.

## D4. 사장님이 admin 에서 직접 쓰는 글은 **어떤 게이트도 검사하지 않는다**

**발견**: 2026-09-15 독립 감사(`P6-6-audit.md` R-9).

### 무슨 일이 벌어지나
금지어·실증 불가 표현 검사는 전부 **소스 파일**을 본다 — `check-legal-disclosures.sh` 는 `app lib actions components tests i18n messages styles` 를 grep 하고, vitest 목록은 `messages/*.json` 과 컴포넌트 코드를 읽는다.
그런데 공지·팝업·갤러리 설명·대표 노선 라벨은 **DB 행**이다. 사장님이 관리자 화면에서 타이핑한 글자는 어느 검사도 거치지 않고 그대로 공개 화면에 렌더된다.

즉 사장님이 공지에 **"면허 보유"**(여객자동차 운수사업법상 전세버스는 **등록제**다) 나 **타사 상호**, **"업계 1위"** 같은 문장을 쓰면 **막는 것이 아무것도 없다.**
법적 책임은 광고주인 사장님께 간다. 우리가 코드에서 아무리 막아도 이 경로는 열려 있다.

### 왜 이것을 "결함"으로 적나
CLAUDE.md §3 의 절대 규칙들은 **사이트가 무엇을 말하는가**에 대한 규칙이지 **어느 파일에 있는가**에 대한 규칙이 아니다. 지금 구현은 후자만 강제한다.

## D5. 관리자 화면에 **로그아웃 버튼이 없다**

**발견**: 2026-09-15, P5-7(운영 매뉴얼) 구현자가 화면을 훑다 발견. 컨트롤러 코드 확인.

Supabase 세션은 리프레시로 계속 연장되므로, 한 번 로그인한 브라우저는 **사실상 무기한 로그인 상태**로 남는다.

**왜 문제인가**: 사장님이 사무실 공용 PC 나 남의 기기에서 한 번 들어가시면 그 세션이 남는다. 그 화면에는 **손님 이름과 원문 전화번호**가 그대로 보인다(마스킹하지 않는 것이 의도다 — 전화를 거셔야 하니까).
운영 매뉴얼에 "쓰고 나면 로그아웃하세요"라고 쓸 수조차 없다 — 버튼이 없다.

**조치**: 관리자 레이아웃에 로그아웃 버튼 + `signOut()` 서버 액션. 작다. **P5-11 로 처리한다.**
권한을 **주는** 변경이 아니라 **거두는** 변경이라 위험이 낮다. 다만 인증 경로이므로 컨트롤러가 직접 확인한다.

### ✅ 버튼은 생겼다 — 그런데 **로그아웃이 DB 접근을 끊지는 못한다** (P5-11 실측, 2026-09-16)

`actions/admin/session.ts` 의 `signOutAdmin` 이 들어갔다. 게이트 화이트리스트를 **늘리지 않고** 첫 문장에 `requireAdmin()` 을 두어 기존 게이트를 **탄다**. 폼 제출(POST)이라 프리페치·크롤러가 사장님을 로그아웃시키지 못한다.

**보장하는 것** (로컬 실측): 브라우저 쿠키 삭제 · 리프레시 토큰 회수(`refresh_token_not_found`) · scope 기본이 `global` 이라 **모든 기기**의 세션이 끊김 · `GET /auth/v1/user` → **403 session_not_found** 라 관리자 화면은 즉시 닫힌다.

**🔴 보장하지 못하는 것**: 로그아웃 뒤에도 **같은 access_token 으로 PostgREST 는 200 을 준다**(`rpc/is_admin` → `true`, `reservations` → 200). PostgREST 는 **서명만 보고 세션 존재를 묻지 않기** 때문이다. 즉 쿠키를 복사해 간 사람은 **토큰 만료(1시간)까지** DB 에 직접 질의할 수 있다.
→ 그래서 운영 매뉴얼의 **"공용 컴퓨터에서 쓰지 마세요"** 를 지우지 않고 **"로그아웃이 생겼지만 그것만으로 충분하지 않다"** 로 바꿨다. 버튼이 생겼다고 경고를 내리면 안 된다.
→ 완전히 닫으려면 토큰 수명을 줄이거나 JWT 검증에 세션 확인을 더해야 한다(Supabase 설정 영역). **오픈 게이트 재검토 항목**으로 둔다.

## D8. **노출을 끈 앨범을 지우면 안의 사진이 손님에게 다시 보인다**

**발견**: 2026-09-16, P5-11 구현자가 "앨범을 지우면 사진이 어떻게 되나" 를 코드로 확인하다 발견. 컨트롤러가 원문 확인.

### 무슨 일이 벌어지나
`supabase/migrations/0008_gallery_albums.sql:61` — `album_id int references gallery_albums (id) **on delete set null**`
같은 파일의 공개 정책:
```sql
create policy gallery_select_active on gallery for select using (
  active
  and (album_id is null or exists (select 1 from gallery_albums a where a.id = gallery.album_id and a.active))
);
```

사진이 **활성**이고 앨범이 **비활성**이면 `exists` 가 거짓이라 **숨겨진다**. 그런데 그 앨범을 **삭제**하면 `album_id` 가 `null` 이 되고, 정책의 **`album_id is null` 가지가 열려** 같은 사진이 **공개된다.**

**사장님의 머릿속**: "이 앨범은 안 보이게 해 뒀으니 이제 지워도 되겠다" → **지우는 순간 손님에게 보인다.** 정반대 결과다.

### 왜 `on delete set null` 자체는 옳은가
그 줄의 주석이 이유를 적어 두었다 — `cascade` 였다면 앨범 하나를 지울 때 사진 수백 장의 DB 행이 사라지고 **Storage 객체는 남아 복구 불가능한 고아 파일**이 된다. 행을 남기는 선택은 옳다. **문제는 남긴 행의 공개 여부가 바뀐다는 것**이다.

### 지켜야 할 불변식
**삭제가 공개 여부를 바꾸면 안 된다.** 지우기 전에 안 보이던 사진은 지운 뒤에도 안 보여야 한다.
(반대로 보이던 앨범을 지우면 사진은 계속 보이는 것이 맞다 — 그건 놀랍지 않다.)

### 선택지
| # | 방법 | 비용 | 위험 |
|---|---|---|---|
| A | 앨범 삭제 시 **그 앨범이 비활성이었으면** 사진을 `active = false` 로 내린다(트리거 또는 관리자 액션) | 작다 | 공개 여부가 정확히 보존된다. 트리거면 경로와 무관하게 보장 |
| B | 정책에서 `album_id is null` 가지를 없앤다 | 작다 | **앨범 이전의 평면 사진이 전부 사라진다** — 지금 공개 갤러리의 기본 상태다. 안 된다 |
| C | 확인창 문구로만 경고 | 0 | 사장님이 읽고도 의도를 오해할 수 있고, 이미 지운 뒤에는 되돌릴 방법을 따로 찾아야 한다 |

### 현재 결정 (컨트롤러, 2026-09-16)
**A + C.** 불변식을 DB 가 지키게 하고(A), 확인창에도 무슨 일이 일어나는지 적는다(C).
**미착수** — 별도 태스크. 마이그레이션이 필요하므로 CLAUDE.md §3 의 기본 권한 규약(새 객체는 공개 롤에 열린다)을 함께 지켜야 한다.
지금은 운영 매뉴얼 6장에 경고가 들어가 있다(P5-11).

## D7. 잠금 완전성 게이트의 주석 제거기가 **파일 절반을 조용히 건너뛸 수 있다**

`tests/db-test-preconditions.test.ts` 의 `stripTsComments` 는 이렇게 생겼다:
```js
src.replace(/\/\*[\s\S]*?\*\//g, "").replace(/(^|[^:])\/\/.*$/gm, "$1")
```

**문자열 리터럴을 구분하지 못한다.** 테스트 코드에 `"components/home/**"` 같은 **글로브 패턴 문자열**이 있으면 그 안의 `/*` 를 블록 주석 시작으로 읽고, 파일 뒤쪽의 아무 `*/`(예: JSDoc 닫는 줄)까지를 통째로 지운다.

**왜 심각한가**: 이 게이트의 존재 이유가 "잠금을 빠뜨린 DB 블록을 **매번** 잡는다" 인데, 스캐너가 조용히 눈을 감으면 **green 이 아무것도 증명하지 못한다.** 이 프로젝트가 반복해서 겪은 실패 모양 그대로다(2026-09-11 빈 값 숨김, 관리자 게이트 정규식 2회 무력화).

P6-6 독립 리뷰어가 **같은 결함이 두 번째 파일에도 있음**을 찾고 **실제로 게이트를 통과시켰다.** `tests/copy-rules.test.ts:38` 의 `stripComments` 가 같은 정규식이다.

```

```
**두 게이트를 모두 통과했다.** 같은 문장을 `/**` 짝 없이 심었을 때는 3건이 빨갛게 떴으므로, 원인은 문장이 아니라 **제거기**다.

## D9. 🔴 공개 키만으로 **예약 전체를 외부로 빼돌릴 수 있었다** — 코드 수정 완료, **원격은 아직 열려 있다**

**발견**: 2026-09-16. P5-12(0016) 구현자가 콘텐츠 표를 정리하다 개인정보 표에도 같은 권한이 남은 것을 보고 → 컨트롤러 실측 확인 → P5-13(0017)이 **실제로 공격을 성공시켜** 증명.

### 무엇이 가능했나
`CREATE TRIGGER` 는 **표의 `TRIGGER` 권한**과 **이미 존재하는 트리거 함수의 EXECUTE** 만 요구한다(스키마 CREATE 불필요 — 0012 헤더의 옛 기술이 틀렸고 0016 이 정정했다).
- `reservations`·`notifications_log` 에 **`anon`·`authenticated` 둘 다 `trigger` 권한**을 갖고 있었다(Supabase 기본 권한).
- `supabase_functions.http_request` 는 그 롤들이 **실행할 수 있는** 트리거 함수이고, **행이 바뀔 때마다 외부로 HTTP 요청**을 보낸다.

**RLS 는 이것을 전혀 막지 못한다.** 트리거는 정책이 아니라 권한의 영역이다.

### 이론이 아니다 — 실제로 붙였다 (0017 실측)
적용 **전**:
```
[anon → reservations] CREATE TRIGGER 성공
[anon → notifications_log] 성공
[authenticated → reservations] 성공
[authenticated → notifications_log] 성공
```
적용 **후**: 네 조합 전부 `SQLSTATE=42501 permission denied`.
롤 전환이 진짜 일어났는지 `current_user` 로 따로 확인했다 — postgres 로 성공한 것을 오독하면 정반대 결론이 난다. 탐침은 마이그레이션과 테스트에 **상설**로 들어갔고, **대조군으로 `service_role` 은 성공해야** 통과한다.

**새어 나갈 수 있었던 것**: 접수가 들어올 때마다 고객 **성명·전화번호·이메일·문의내용**과 **문자 수신처·본문** 전부.

### 함께 회수한 것 — `anon` 의 `select`
두 표를 `anon` 으로 읽는 코드가 **하나도 없다**(최근 접수 피드·예약확인·문안 로더·파기 크론 전부 서비스 롤, 관리자 둘은 authenticated). 0009 의 정책 셋도 전부 `to authenticated` 다.
즉 지금의 "0행" 은 **정책이 없어서** 나오는 결과이고, **anon 용 select 정책 한 줄이면 고객 표가 공개된다.** 회수해서 방어선을 하나에서 둘로 만들었다.
거동 변화: anon 읽기가 `200 []` → **`401` + `42501`**. 관련 단언 하나를 그에 맞게 고쳤고, 문안 로더가 거부를 **삼키지 않고 throw** 하게 했다(삼키면 "권한 없음" 과 "예약 없음" 이 구분되지 않는다).

### 🔴 원격은 아직 이 상태다
원격에는 **0011 까지만** 적용돼 있다. `0012`~`0017` 이 전부 대기 중이므로 **지금 이 순간 원격 데이터베이스에는 위 권한이 그대로 열려 있다.**
사이트가 아직 공개되지 않아 실피해 가능성은 낮지만(anon 키는 배포된 프런트엔드에 실린다 — 아직 배포 전), **적용 우선순위를 올릴 근거**다.
적용은 `supabase db push` 가 **자동 승인 정책(Production Deploy)에 막혀** 있고 우회하지 않았다. 사용자 승인이 필요하다. 절차는 `docs/ops/migration-runbook.md`.

**원격 적용 시 알아 둘 거동 변화**: anon 키로 `/rest/v1/reservations` 를 치는 외부 모니터링이 있으면 `200` → `401` 로 바뀐다(저장소 안에는 그런 경로가 없다).

## D10. 로그인한 사용자는 **쓰기 권한만으로** 콘텐츠 표를 잠글 수 있다

**발견**: 2026-09-17, P5-15(0019 `MAINTAIN` 회수) 구현자가 범위 밖에서 보고. PostgreSQL 명세로 확인.

### 무엇이 가능한가
PostgreSQL 은 `ACCESS EXCLUSIVE` 같은 강한 표 잠금을 **`MAINTAIN` 또는 `UPDATE`·`DELETE`·`TRUNCATE`** 권한으로 허용한다.
0019 가 `MAINTAIN` 을 회수했지만, `authenticated` 는 관리자 화면 때문에 콘텐츠 여섯 표(`notices`·`popups`·`gallery`·`gallery_albums`·`showcase_routes`·`vehicles`)에 **`UPDATE`·`DELETE` 를 여전히 갖는다.** 그래서 **로그인만 하면**(관리자가 아니어도) `lock table notices in access exclusive mode` 가 된다 — 0019 전후 모두 로컬에서 성공을 확인했다.
RLS 는 이것을 막지 못한다. 게이트는 그 쓰기 권한을 **의도적으로 허용**하므로 빨갛지 않다.

개인정보 두 표(`reservations`·`notifications_log`)는 `authenticated` 에게 `SELECT` 만 남아 있어 **잠금이 거부된다**(0012·0017).

### 왜 지금 급하지 않은가
**공개 회원가입이 막혀 있다**(D2, 2026-09-13 조치). 따라서 지금 `authenticated` 롤을 가질 수 있는 것은 **관리자 명단에 있는 사람뿐**이다. 관리자는 어차피 그 표를 고칠 수 있다.
PostgREST 는 `LOCK` 을 노출하지 않으므로 공개 API 로 도달할 경로도 없다. 도달하려면 SQL 을 직접 칠 수 있어야 한다.

### 무엇이 이것을 위험하게 만드나
**공개 가입이 다시 열리는 순간**, 아무나 계정을 만들어 공지·갤러리 표를 잠가 관리자 화면과 공개 화면을 멈출 수 있다. D2 가 "다시 켜지 말 것" 이라고 적은 이유가 하나 더 늘었다.

### 선택지
| # | 방법 | 비용 |
|---|---|---|
| A | 관리자 쓰기를 **definer 함수**로 옮기고 `authenticated` 의 표 쓰기 권한을 회수 | 관리자 화면 쓰기 경로 전면 수정 — 0010 이 예약 전이에 한 방식 |
| B | 관리자 전용 **별도 롤**을 두고 `authenticated` 에서 쓰기를 떼어 냄 | Supabase 인증과 롤 매핑 설계 필요 |
| C | 그대로 두고 공개 가입 차단(D2)에 기댄다 | 0 |

### 현재 결정 (컨트롤러, 2026-09-17)
**C — 기록하고 둔다.** 근거: `authenticated` = 관리자 명단이라는 전제가 D2 조치로 성립하고, A·B 는 관리자 화면 쓰기 경로 전체를 바꾸는 설계 변경이라 오픈 직전에 넣을 크기가 아니다.
**전제가 깨지면 재검토 필수** — 공개 가입을 다시 여는 결정, 또는 관리자가 아닌 `authenticated` 사용자가 생기는 설계는 이 항목을 먼저 풀어야 한다.
